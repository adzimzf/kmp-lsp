# Results: square/moshi, 2026-11-06

**Partial run: JetBrains kotlin-lsp is missing.** Its newest published build
(263.6379.0, the top of `RELEASES.md` on 2026-11-06) is an EAP build that
refuses to start: "This build of kotlin-server has expired". So:

- the Kotlin half of definition and references has **no reference** and is
  not scored (kmp-lsp's Kotlin answers are recorded in the raw results);
- Java definition and references are scored against jdtls;
- completion is scored against the source itself for both languages.

Re-run with a fresh kotlin-lsp build to fill in the Kotlin side.

**Corrections found later** (fixed in `compare.sh`; rerun it for clean
numbers):

- kmp-lsp ran **without its JAR-indexer sidecar** (a normal install has
  it), so it had no symbols from compiled library jars.
- The **"no dep sync" rows are inflated**: that run came after a
  dependency-syncing run that had already downloaded sources jars into the
  shared Gradle cache. Run first on a clean cache, as `compare.sh` now
  does, it scores 72% on Java definitions with the sidecar (56–58%
  without), against 75% with dependency sync.
- The dependency-sync setting was passed as `"on"`, which kmp-lsp doesn't
  accept (`"auto"` / `"off"`). It fell back to its default, `auto`, so the
  sync did run.

Readings:

- *ready* = both probes answer correctly; *settled* = no `$/progress`
  activity for 5 s; queries start after settled.
- kmp-lsp's peak RSS with dependency sync includes the Gradle daemon its
  sync starts (process-tree memory); jdtls's includes Buildship's Gradle
  daemon the same way.
- *Class-level* definition matches: jdtls can't open Kotlin sources, so for
  Java calls into moshi's Kotlin core it answers with the compiled class
  (`jdt://…/JsonReader.class`) while kmp-lsp opens `JsonReader.kt` at the
  declaration. Those count as right, and are shown separately.
- kmp-lsp's Java completion returns 500 items and the harness keeps the
  first 300, so its "anywhere" is a lower bound.

## What it found in kmp-lsp

- Java `String` in type position resolves into a Kotlin file
  (`Iso8601Utils.kt`) instead of `java.lang.String` — 5 of the 9 wrong
  Java definitions.
- `list.add(…)` / `map.put(…)` on JDK collections resolve to same-named
  moshi members (`Moshi.Builder.add`, `LinkedHashTreeMap`).
- Java member completion isn't filtered by receiver type: 500 items, the
  right member in the top 10 only 5% of the time (jdtls: 38%).
- Kotlin completion is empty for 25% of member accesses (library or
  inferred receivers).
- Find-references in Java: 64% precision / 63% recall against jdtls.
